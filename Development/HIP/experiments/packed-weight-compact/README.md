# Ordinary compact packed-weight storage: expand-only trial

CPU preparation, not numerically accepted or deployed. No kernel, module, FP8 encoding, reduction order, activation, scalar precision, driver or VMM changes.

Current loader packs FP8 matrices into the prefix of their original F32 allocations. `PackedVitWeight` still uploads `v.size()*4`. Expand4096×1024 has exactly4194304 floats and no scalar tail: 16MiB capacity, 4MiB consumed bytes. Contract has a4096B tail and projection has scales at original offsets; neither is touched. Current QKV Frag8 already resizes to compact storage and is not counted as newly reclaimable.

`prepare.py --repo REPO --out PRIVATE` copies current host headers and original fullFrame benchmark to an isolated layout and patches only its loader. Default `HIP_COMPACT_VIT_EXPAND=0` compiles the original function text. Explicit1 requires the fragment FP8 byte-input nonfused expand selector, no M2/M4/tiled-input variant, exact block31..38-expand.f32 names, rows4096/columns1024/no tail and ordinary allocation mode. Other paths retain the original loader. New `@vit-frag@compact-expand` keys must not coexist with corresponding legacy keys; mixing is rejected. The packed host vector is shortened, dead ranges consumed/cleared, then a single persistent ordinary hipMalloc4MiB is uploaded. The old16MiB GPU allocation is never created; no old pointer aliases are retained. Pointers/resources remain owned in the usual network weight cache until synchronized network destruction. No mid-session preference switch is introduced.

The only compact consumer is unchanged `vit_expand_blocked_fp8_frag_bytein` → `vit_expand_blocked_body<true,true,true>` → `vit_weight_fragment_native`. For rows0..4095, K16=0..1008, gr0/1, byte0..7, its accesses bijectively cover bytes[0,4194304). The eight ledger ordinals59/65/71/77/83/89/95/101 have distinct FW resources98/102/106/110/114/118/122/126, each used only as this function's arg1 at offset0. `prove_expand.py` exhaustively verifies this address map and compares actual captured packed bytes at every access. CPU inverse/live-byte diff0; dead bytes are discarded, not re-quantized. All eight sizes imply a96MiB logical capacity reduction **for this frozen1152/640 profile**, not measured current residency or FPS. Constructor-only `COMPACT_WEIGHT` logs must confirm eight4MiB allocations and zero legacy key retention in the real fullFrame gate.

`unit.cpp` uses the canonical11a25ae3… deep_fast-packed-fast module and actual captured640-token operands. It runs full16MiB weight twice, frees it, then allocates exactly4MiB and runs twice; all four full FP8 outputs must equal captured gold, original repeat, finite and a256B output tail guard. Input/weight/module/output SHA preflight belongs to the run wrapper. No timers or new shader are needed. GPU matrix-prefix readback independently confirms the uploaded weight bytes; scalar load upper bounds are established by the source+exhaustive address proof, not just output equality. Driver free-memory deltas are logged as approximate allocation observations, not resident peaks.

Next gates: strict single-operator hardware gold; original/current fullFrame macro0 vs macro1 same frozen HDR, actual geometry/source/modules/style/seed/MP1/AE0/historyoff and production PulseAuto/PDL; full output and first/last hashes; exact requested/held weight byte logs and driver memory scope; only then short frame timing if main schedules it. Cold allocations/upload/diagnostic readbacks stay outside timing. Necessary steady work remains charged. A lack of memory pressure may yield no FPS improvement despite reclaimed capacity. No game installation or default change is authorized by this trial.
